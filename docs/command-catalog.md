# 명령 카탈로그 v1.0 (확정)

> 확정일: 2026-07-14
> 본 문서는 프로젝트의 명령 범위를 정의하는 정본이다. 명령 추가·변경 시 본 문서를 먼저 갱신한다.

## 프로젝트 목표

게임 개발자가 직접 해야만 하는 작업(아이디어·디렉션, 로직의 설계 결정, 재미/감각 판단, 최종 검수) 이외의 대부분의 작업을 **명령만으로** 처리할 수 있는 구조를 확보한다. 사람/AI의 경계는 고정이 아니라 경제적 기준(사람이 직접 하는 편이 코스트·시간이 적게 드는가)으로 판단하며, 파이프라인 성숙에 따라 이동할 수 있다.

## 설계 원칙

1. **완벽한 단일 진입점을 고집하지 않는다.** 단, 플레이/디자인/사운드 3요소는 유기적으로 동작해야 한다.
2. **양방향 워크플로를 지원한다.** play-first(로직 먼저 → 디자인 입히기)와 design-first(핵심 컨셉 디자인 먼저 → 플레이 개발) 모두 성립해야 한다.
3. **사운드는 후순위이며 SE(효과음) 중심이다.** BGM은 최소 기능만 유지한다.
4. **로어(설정/세계관)는 4번째 트랙이 아니라 기반 계층이다.** 모든 트랙이 참조하는 단일 정본(canon) 역할을 한다.
5. **모든 실행 명령은 「생성 → 자동 검증 → 사람 검수 → 반영」 흐름을 따른다.**

## 성공 지표 (KPI)

- 명령 1회당 사람의 개입 시간(분)
- 명령 1회당 사람의 개입 횟수

---

## 기반 계층 — 로어/설정 (lore)

| 명령 | 설명 |
|---|---|
| `lore init` | 컨셉 문답을 통해 세계관 골격 문서 생성 |
| `lore add <항목>` / `lore edit <항목>` | 설정 추가·수정. 관련 항목과 자동 교차 검토 |
| `lore query <질문>` | 설정 조회. 사람용이자 다른 명령의 컨텍스트 주입용 |
| `lore check` | 정본 모순·공백 검사 |
| `lore export <대상>` | 게임 내 텍스트 생성 (아이템 설명, 대사, UI 문구 등) |

## 플레이 트랙 (play)

| 명령 | 설명 |
|---|---|
| `play spec <기능>` | 아이디어를 구현 명세로 변환. **사람 승인 지점** |
| `play build <명세>` | GDScript 구현 + 씬 구성 + 플레이스홀더 에셋 자동 배치 (매니페스트 등록) |
| `play test` | Godot headless 스모크 테스트 및 규칙 검증 |

## 디자인 트랙 (art)

| 명령 | 설명 |
|---|---|
| `art concept <주제>` | 컨셉 후보 복수 생성. design-first 진입점 |
| `art lock` | 선택된 컨셉을 스타일 가이드로 고정. 이후 모든 생성의 기준 |
| `art gen <에셋 명세>` | 생성 → 후처리(배경 제거, 리사이즈, 패킹) → 임포트까지 일괄 |
| `art reskin <씬/범위>` | 매니페스트 기반으로 플레이스홀더를 실제 에셋으로 일괄 교체 |

## 사운드 트랙 (se / bgm) — 후순위

| 명령 | 설명 |
|---|---|
| `se gen <이벤트 목록>` | 게임 이벤트 기반 효과음 생성 + 포맷 정규화(OGG, 라우드니스) |
| `se attach` | 매니페스트 기반으로 코드 내 이벤트 지점에 효과음 자동 연결 |
| `bgm gen` | 루프 가능한 앰비언트 베드 절차 합성 (`bgm_gen.py`, ffmpeg). 최소 기능 — 멜로디·편곡은 범위 밖 |
| `bgm prep` | 외부 음원을 루프용으로 다듬기 (`bgm_prep.py`) — 앞뒤 무음 트림 + 루프 경계 페이드. 정규화는 `se_post.py normalize` |

## 오케스트레이션 — 공통

| 명령 | 설명 |
|---|---|
| `plan <목표>` | 목표를 트랙별 태스크로 분해, 실행 순서 제안 |
| `verify` | 임포트/테스트/네이밍 규칙 통합 검증 게이트 |
| `review` | 사람 검수 큐. 승인/반려 + 한 줄 피드백 |
| `status` | 프로젝트·태스크 현황 |

## 대표 워크플로

### play-first (로직 먼저)
```
lore init(선택) → play spec → [승인] → play build → play test
→ art lock → art reskin → se gen → se attach → verify → review
```

### design-first (컨셉 디자인 먼저)
```
lore init → art concept → [선택] → art lock
→ play spec → [승인] → play build → art gen/reskin → se gen → se attach → verify → review
```

## 유기성의 핵심 장치: 에셋 매니페스트

`pipeline/manifest.json` — "어떤 노드/이벤트가 어떤 에셋을 필요로 하는가"의 단일 기록.

- `play build`: 플레이스홀더 생성 시 매니페스트에 항목 등록
- `art reskin` / `se attach`: 매니페스트를 읽어 교체·연결
- `verify`: 매니페스트와 실제 파일의 정합성 검사

스키마: `pipeline/schemas/asset-manifest.schema.json` 참조.
